# Papilio 1.4.0

Application registration paths accept both Python files and nested packages:
`routers`, `tools`, `function_tools`, `providers`, `infra.tables` and
`domain.documents`. For example, `routers/admin/categories.py` is discovered
without forwarding imports. Keep package initializers empty and definitions in
the leaf files.

Existing flat layouts remain supported. Discovery retains the application's
selected module roots and visits files in package order. Broken imports inside
selected subtrees fail startup; absent registration paths remain optional.
Unrelated domain, application and infrastructure files are not scanned.

Provider classes, router/tool objects and document classes are registered once.
Providers must still be defined in the discovered file rather than re-exported
from another module. Tables load before providers.

Moving an HTTP handler can affect route order: preserve unambiguous paths and
verify matching through the application. Moving a tool with an implicit
module-derived key can change its identity; retain explicit keys when moving
public tools. Task discovery belongs to Papilio Tasks and is unchanged.

No database or search-index migration is required by this framework release.
See [module discovery](../guide/modules.md#startup-discovery) for the contract.
